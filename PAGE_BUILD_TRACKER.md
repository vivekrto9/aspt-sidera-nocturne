## Page Status Contract

Allowed page statuses:

- `TODO`: unowned and available to claim.
- `IN PROGRESS`: owned by exactly one session. The owner builds its sections in the listed order.
- `DONE`: every listed section is implemented, reviewed, responsive, localized, Content Studio editable where applicable, and committed.
- `REMOVED`: intentionally retired by an explicit product decision. The route and active implementation are absent, the row is retained only as a cross-session tombstone, and no session may reclaim or recreate it without a new explicit user decision.

Sections do not receive individual status values, but every section has an approval-and-commit gate.

For an `IN PROGRESS` page, the `Current section` column identifies the section being built. Sections before it in the ordered list are treated as implemented, explicitly approved, and committed; sections after it are not started. A page remains `IN PROGRESS` until the entire page is approved.

## Section Approval And Commit Contract

Every explicit user approval of the current section must be followed by an isolated commit before the tracker advances to the next section.

1. Re-read the live tracker and confirm the page owner and current section.
2. Record the user's approval and remove only temporary review helpers introduced for that section.
3. Rerun the section's focused checks and `git diff --check`.
4. Commit only the files owned or necessarily changed by that approved section. Exclude shared trackers, activity logs, demo-only files, Content Studio error logs, and unrelated or concurrently owned changes from the commit.
5. Record the commit hash in the activity note, then advance `Current section` to the next ordered section.
6. If the approved section cannot be isolated safely from unrelated changes, stop and report the overlap instead of creating a mixed commit.
7. The final section approval follows the same isolated-commit workflow; only after its commit may the page move to `DONE`.

3. A flow-group owner must implement the group in the documented start-to-end order. After one grouped page is approved, marked `DONE`, and committed, that session's next page must be the next `TODO` page in the same group.
4. A flow-group owner may not switch to an independent page or another group while its current group still contains unfinished pages unless the user explicitly releases or reassigns the group.
5. Independent pages are not reserved by a group. Any session without an active page or group may freely claim an independent page whose status is `TODO`.
6. A navigation link by itself does not make two pages a group. Group pages only when they share a continuous user flow, state handoff, or tightly coupled page-local contract.
7. Before editing page code, change that page to `IN PROGRESS`, record the session owner, and set `Current section` to the first section. Other pages in an owned group remain `TODO` until their turn, but are unavailable to other sessions.
8. Divide every page into the ordered sections listed in this tracker and build only one section at a time.
9. Inspect the exact matching `.dc.html` reference section before implementing it.

## Global Heading Cascade Guard

Historical failure discovered during the now-removed P-06 Composite Chart Intro:

- `BaseLayout.astro` loads `src/styles/base.css` on every customer page.
- The legacy global `h1 { max-width: 850px; ... }` rule therefore constrains every rendered page-level `h1` unless the owning component explicitly overrides it.
- `PageIntro` renders its title through `SectionHeading` as an `h1`. In the failed Composite state, the outer centered content measured `1184px`, but the `h1` remained an `850px` block at the left edge. Setting the nested title row to `inline-size: 100%` only made it fill that incorrect `850px` parent, so the phrase still appeared left-aligned.

Required diagnosis and fix pattern:

1. Measure the viewport, page container, shared heading content, rendered `h1`, nested title wrapper, and the visible title fragments. Compare their centers, not only their declared CSS.
2. Identify the first incorrectly constrained ancestor and fix ownership there. Do not keep compensating on descendants.
3. A page-specific need must use an existing shared variant or an explicitly approved opt-in variant. The retired Composite page temporarily used a `PageIntro` `wide` measure, but that Composite-only variant was removed with the page; it is not an available implementation shortcut for future sessions.
4. A future global cleanup must scope or remove the legacy bare `h1` layout rule in `base.css` only after the shared-default workflow is approved and every direct `h1` usage is audited. Do not silently change the global default from an individual page session.
5. Verify the final rendered centers at the target desktop width and at `390px`, confirm intended wrapping, and confirm `document.documentElement.scrollWidth <= window.innerWidth`.

## Component Discovery During Page Work

When an approved page section needs UI that is not already listed in `COMMON_COMPONENTS_TRACKER.md`, do not immediately create it as either shared or page-common UI.

Follow this classification sequence before implementation:

1. Search the complete reference set, current source, imports, and usages with `rg`.
2. Confirm that no approved shared component already covers the structure, semantics, behavior, and accessibility contract through existing props, slots, or variants.
3. If the component is independently required by two or more unrelated pages:
   - confirm those usages have the same semantic purpose, structure, behavior, responsive needs, and accessibility contract;
   - treat differences in copy, color, optional icons, or other minor presentation as props or bounded variants when one component can safely cover them;
   - add the candidate to `COMMON_COMPONENTS_TRACKER.md`, mark it `IN PROGRESS`, and record the owner before creating files;
   - build it under `src/components/shared` with mirrored shared styles and focused contract tests;
   - mount all required variants and states on `/demo` for user review;
   - do not resume the page section until the new shared component is approved and its temporary successful review showcase is removed according to the common-component workflow.
4. If the UI is reused by two or more sections of the same page but is not independently useful across unrelated pages:
   - create it under `src/components/<page>/common`;
   - mirror it under `src/styles/<page>/common`;
   - add `src/data/locale/<page>/common` only when the component owns visible copy;
   - keep section-specific copy and placement caller-owned.
5. If the UI repeats multiple times inside only one section:
   - keep it section-local or as a private helper beside that section;
   - do not promote it to page-common solely because a list renders several instances.
6. If the UI appears only once, keep it in the owning section.
7. Do not generalize from speculative future reuse. Promotion requires at least two verified real usages.
8. If implementing the new component would require editing an existing shared component, follow the mandatory global-default versus page-specific scope decision before editing.

### Working Inline-Editing Contract

This contract records the failure found and fixed during the Home Hero implementation. Every page session must follow it so a field cannot look editable while rejecting the actual edit interaction.

#### Attribute wiring

- Treat `data-builder-edit` as a presence marker. An empty HTML boolean-style attribute is still a valid edit marker.
- Never validate this marker with `Boolean(element.dataset.builderEdit)` or another truthiness check because an empty serialized attribute produces an empty string. The shared editor correctly checks `element.hasAttribute("data-builder-edit")`.
- When Builder attributes pass through a component prop typed as strings, preserve boolean `true` as the truthy string `"true"` exactly as Home's `componentEditAttributes` adapter does. Never convert it to `""`, `false`, or omit it.
- Pass the complete Builder identity together: `data-builder-collection`, `data-builder-entry`, `data-builder-locale`, and `data-builder-field`. Missing any one of these makes the field non-editable.
- Attach edit attributes to the exact visible text element. For editable input or textarea placeholder copy, attach them to the real `input` or `textarea`, not only to its surrounding label or wrapper.
- Every shared Header usage must prepare its language options from the `site_chrome/main` fields named `language_option_<locale-code>_label` and pass each field's `chromeEdit(...)` attributes through the option's required `editAttributes`. Do not render `activeLocales[].nativeName` directly after Content Studio content has been resolved; it is only the fallback default.
- Reuse the shared `BuilderClient.astro` editing lifecycle. Do not add page-specific `contenteditable` scripts, dirty-state stores, save handlers, or Builder CSS.

#### Required editing behavior

- Clicking a registered text field in Edit content mode must add the active editing state and `contenteditable="plaintext-only"`.
- Typing must update the pending change immediately through the shared `input` listener. The dirty count must increase and Save draft must become enabled before blur.
- Returning the text to its original value must clear that pending change.
- Pressing Escape must restore the original rendered content, remove the active editing state, clear the field's pending change, and return Save draft to disabled when no other edits remain.
- Enter or blur may finish the local edit through the shared lifecycle. Save draft and Publish changes remain explicit Content Studio actions and must never be triggered by a page-owned field handler.
- Placeholder editing must temporarily expose the placeholder as editable text without overwriting the user's current input value. Password inputs must restore their original type, value, and placeholder behavior after editing.
- The active context chip must show the correct locale and `collection/entry`, and it must identify when the selected field has an unsaved change.
- Save failures must surface the safe server message or HTTP status through the shared editor. Pages must not swallow errors or show fake success.

#### Theme ownership

- `src/builder/BuilderStyles.astro` is the single owner of Content Studio and inline-edit styling.
- The approved Sidera treatment uses the repository's warm brown and terracotta Builder tokens, including `--builder-edit-outline: #cb6b4e` and `--builder-edit-surface: rgba(203, 107, 78, 0.09)`.
- Do not copy Divyastra's red/gold editor palette into a page stylesheet and do not override `.builder-*`, `[data-builder-edit]`, or `[data-builder-editing]` selectors from page CSS.
- If a real Builder behavior or global theme change appears necessary, stop and ask whether the user wants a default shared Builder change or a page-specific integration fix before editing shared Builder files.

For the first section and whenever a page introduces new edit-binding shapes:

1. Open the real route with authorized local editor access and `?preview=1`; do not verify only on `/demo`.
2. Run `node scripts/validate-content-studio-local.mjs`. A physical-column failure blocks review. Resolve warnings through the real first-save/full-bootstrap flow and rerun the check.
3. Confirm the launcher shows the page's correct active locale, collection, entry, saved-draft state, and review targets.
4. Enable Edit content and click one representative field for every binding shape used by the page: plain text, rich/nested text, CTA label, and input or textarea placeholder where applicable.
5. Type temporary content without saving it. Confirm the rendered value changes, the dirty count increments, Save draft becomes enabled, and the selected context reports the unsaved edit. Press Escape and confirm the original value and clean state are restored.

Complete the reversible persistence workflow in `CONTENT_STUDIO_ERROR_LOG.md`: Save draft for one field, Save draft for two fields in one target, reload to confirm persistence, restore the original values, Save draft again, and confirm Review changes contains no unintended test copy. ## UI-Derived Integration Requirements

UI implementation cannot define a final backend API by itself. It may only document the consumer requirements that are observable from the approved page flow. This handoff keeps the UI stable while leaving backend architecture, security, persistence, and operational decisions to a separately owned backend task.

### What a UI page owner may define

- The user action or event that needs integration.
- The user-entered or page-held inputs required by that action.
- The prepared display data the UI needs in return.
- The page-local loading, empty, success, validation, and general failure presentations.
- The visible field or region where each class of validation problem should appear.
- The expected navigation or UI transition after a successful action.
- Whether an existing API already satisfies the requirement without modification.
- Open questions that a backend owner must resolve.

### What a UI page owner must not define

- New endpoint paths or HTTP methods.
- Database tables, columns, storage models, or migrations.
- Authentication, authorization, CSRF, session, or token behavior.
- Rate limits, retry behavior, idempotency, queues, or provider architecture.
- Final server-side validation rules or stable server error codes.
- Transaction boundaries, persistence behavior, or external-service contracts.
- Fake success behavior on a real page route.

## Localization And Content Studio Contract

### Required languages

The approved site languages are:

- `es` — Español
- `fr` — Français
- `pt` — Português
- `ru` — Русский

### Required implementation pattern

Use the proven Divyastra and Co-Star flow:

```text
request URL ?locale=
  → getLocaleFromUrl
  → section locale defaults
  → loadPublicPageContent (read-only Content Studio resolution)
  → localized default merged with saved locale content
  → section props
  → shared/page components
  → builderEdit attributes on visible static text
```

Rules:

- Use query-parameter localization exactly as defined in `UI_REFERENCE_WORKFLOW.md`.
- Default English URLs stay clean; non-English internal URLs use `?locale=<code>`.
- Pages choose the locale. Components receive final prepared strings and must not choose a language.
- Locale files mirror page and section folders.
- Every locale resolver returns the requested locale with an English fallback for missing values.
- Keep all locale files structurally aligned with the same stable field keys.
- Every visible static string, CTA label, heading, help message, empty state, and SEO field must have a localized default.
- Every visible static field that the user may edit must be registered in `src/builder/registry.ts`.
- Attach `builderEdit("stable_field_slug")` or the component's edit-attribute prop to the exact rendered text node.
- Content Studio edits are locale-specific. Editing English must not overwrite another language.
- Public page rendering remains read-only. It must never create or mutate Content Studio schema, entries, drafts, revisions, or release rows.
- Runtime/provider data, user input, prices, orders, calculated astrology results, and stored customer data are not static translated copy.
- Avoid one giant page-copy file or one oversized Builder entry. Split large pages into page/section content targets when needed and let `loadPublicPageContent` merge the registered targets.
- Adding or changing Builder fields must preserve deployed content and follow the repository migration and schema tests.

- centered horizontal containment
- a small set of reference-backed maximum-width variants
- responsive inline page padding
- an optional semantic `as` element
- an integration `class`

`Container` must not own:

- vertical padding or section gaps
- surface/background colors
- typography
- page-specific grids
- locale selection
- Content Studio loading
- Header or Footer behavior

Start with only widths demonstrated across multiple references:

- `standard`: approximately `70rem` / `1120px`
- `wide`: approximately `73.75rem` / `1180px`
- `reading`: approximately `47.5rem` / `760px`

Do not add arbitrary numeric width props. Add another named width only after at least two real sections need it.

### Recommended decision: use a separate SectionFrame

Create `src/components/shared/SectionFrame.astro` only after user approval and after its spacing variants are checked against Warm Modern.

`SectionFrame` should own repeated full-width section rhythm through a small set of named spacing variants. Page-section CSS should still own the section's background, special geometry, and one-off reference treatment.

Recommended composition:

```astro
<SectionFrame spacing="standard" class="home-sky-section">
  <Container size="wide">
    <TodaySkySection ... />
  </Container>
</SectionFrame>
```

Do not add `marginTop`, `marginBottom`, arbitrary pixel props, or page-specific surface names to the wrapper.

### Public page shell recommendation

Do not create a universal Header/Footer page shell yet. The references use three meaningful chrome modes:

- standard Header and Footer;
- minimal chart-tool top bar;
- fullscreen/auth/session layouts.

Build the first two standard pages with `BaseLayout`, the approved Header/Footer components, `Container`, and `SectionFrame`. If their Header/Footer and Builder wiring are truly identical, extract a layout under `src/layouts` with explicit `standard`, `minimal`, and `fullscreen` modes. The layout must receive prepared localized chrome content; it must not import every page's locale data.

Layout proposal status: `AWAITING USER APPROVAL`.
