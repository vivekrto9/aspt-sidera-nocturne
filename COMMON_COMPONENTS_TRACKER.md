## Design Direction

Visual thesis: warm editorial astrology built from parchment surfaces, terracotta and brown accents, serif-led typography, fine dividers, spacious composition, and precise astronomical diagrams.

Content plan: global chrome, orientation and page introductions, task-specific content or forms, supporting detail/results, then a focused closing action.

Interaction thesis:

- restrained color, border, and background transitions make every clickable element visibly interactive;
- drawers, dialogs, accordions, menus, and result transitions use short, calm entrance/exit motion;
- chart, calendar, and sky controls provide immediate visual feedback without ornamental animation.

## Status System

Only these three component statuses are allowed:

| Status        | Meaning                                                                                                                     |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `TODO`        | Not being implemented. No session owns it.                                                                                  |
| `IN PROGRESS` | Claimed by one session. Includes coding, verification, placement on `/demo`, and waiting for user review.                   |
| `DONE`        | Implemented, verified, shown on `/demo`, explicitly approved by the user, and removed from the standalone `/demo` showcase. |

`IN PROGRESS` must not be changed to `DONE` merely because the code compiles. User approval after `/demo` review is required.

## Non-Negotiable Component Rules

1. An atom is created only when it is used by more than one molecule. If a primitive belongs to only one molecule, implement it privately inside that molecule instead of adding a shared atom.
2. Every clickable or tappable element must have a visible hover state. It must also have keyboard focus treatment and an appropriate disabled state when disabling is supported.
3. Follow the folder ownership and mirrored component/CSS/locale structure in `../UI_REFERENCE_WORKFLOW.md`.
4. If components share the same semantic structure and differ only in color, text, size, density, alignment, or another bounded visual treatment, use one component with named props or variants.
5. Minor differences do not justify separate components. For example, a text-only CTA and a CTA with a right arrow use the same `Button` component with an optional trailing icon.
6. Do not create a generic component merely because two elements are both rectangular. They must share structure, semantics, and behavior.
7. Components receive final copy and prepared data through props. They do not select the active locale or own Builder field registration.
8. Keep operational values and database-backed identity outside Content Studio edit markers. Only approved static copy receives Builder edit attributes.
9. Use the Warm Modern reference values and Sidera theme tokens. Variants are a naming layer over approved reference treatments, not permission to redesign.
10. Prefer Astro with zero client JavaScript. Add a focused browser script only for behavior that cannot be expressed with HTML and CSS.
11. Preserve reference destinations, query parameters, semantics, and interaction behavior. Internal links must use the repository localization contract.
12. Do not mark a component done until interaction, accessibility, and `/demo` review checks pass.
13. Every component must be mobile responsive. Its layout, text, controls, touch targets, overflow, and interactive behavior must be verified at mobile widths before review.
14. After the user reviews and approves a component, mark it `DONE` and remove that component's standalone showcase from `/demo` before that same session moves another component to `IN PROGRESS`. Other sessions may continue working on their separately claimed components. Remove only the `/demo` example; never remove the approved production component, styles, locale data, or tests.
15. Claiming a component in this tracker must be the first repository edit made for that component. Before creating or changing implementation files, change its status from `TODO` to `IN PROGRESS` and record the session/owner, date, and demo anchor. If it is already `IN PROGRESS`, do not work on it; choose another eligible `TODO` component.
16. Every completed review handoff must give the user the exact absolute repository implementation paths, the exact absolute Asknova `.dc.html` reference paths and relevant sections/states used, the absolute repository path to `src/pages/demo.astro` with the stable `/demo` anchor, and the verification results. Do not start a development server or provide a localhost URL; the user owns the existing server on port `4321`.
17. Do not commit a component before successful user review. After approval, commit only files and isolated shared-file hunks owned by that session. Never include another session's staged, unstaged, or untracked changes.
18. The user globally approved backward-compatible common-component edits whose only purpose is to expose optional Content Studio edit attributes on the exact rendered static-copy nodes. Such hooks must preserve every existing visual, semantic, and behavioral default. This approval does not cover redesigns, default changes, new visual variants, or unrelated contract changes.
19. Shared heading components must explicitly account for globally loaded element selectors. Before changing a nested title wrapper, measure the rendered heading and its ancestors and search `base.css`; `inline-size: 100%` on a child does not escape a constrained parent.

## Known Global CSS Collision — Page Heading Width

The now-removed P-06 Composite Chart exposed a cross-page heading bug that future sessions must not repeat:

- `BaseLayout.astro` loads `src/styles/base.css` globally.
- Its legacy bare `h1` rule applies `max-width: 850px`.
- `PageIntro` composes `SectionHeading` with `headingLevel: 1`, so a centered or wide PageIntro can still contain a left-edge `850px` `h1` even when its outer content is correctly centered and wider.
- A nested slot/title row set to `inline-size: 100%` remains only `850px` because percentage sizing resolves against that constrained `h1`.

The correct bounded fix is at the first constrained owner. The retired page's Composite-only `PageIntro` `wide` measure was removed with that page and is not an available variant. Future pages must use an existing approved variant or request the required page-specific/shared-default permission. Before any broader correction, audit every direct `h1` usage and follow the shared-default permission workflow. Browser verification must compare actual bounding-box centers for the container, `h1`, wrapper, and visible phrase at desktop and `390px`, plus check for horizontal overflow.

## Cross-Session Workflow

Before starting a component:

1. Read this tracker and `../UI_REFERENCE_WORKFLOW.md`.
2. Confirm every dependency is `DONE`, unless the user explicitly authorizes parallel work.
3. Re-read the target row immediately before claiming it. If its status is not `TODO`, do not work on it.
4. As the first repository edit for the component, set it to `IN PROGRESS` and add the session/owner identifier, date, and intended `/demo` anchor.
5. Inspect every reference page listed in the component row before editing implementation files.
6. Check the target repository for an existing equivalent before creating a new component.

While implementing:

1. Create the component in the listed path.
2. Put its CSS in the mirrored `src/styles` path.
3. Put component-owned visible copy in the mirrored `src/data/locale` path only when the component owns copy.
4. Use props and named variants for approved structural variations.
5. Add accessible semantics, hover, focus-visible, active, and disabled states as applicable.
6. Add focused tests for variant contracts or behavior when the component has meaningful logic.
7. Add all supported variants and meaningful states to `/demo` under the component's stable anchor.

Before requesting review:

1. Run focused tests, typecheck, and build.
2. Inspect `/demo` at desktop and mobile widths.
3. Verify keyboard operation and visible focus.
4. Record any known limitation in the component row.
5. Keep the status `IN PROGRESS` with the note `Awaiting user review`.
6. Give the user the exact absolute repository implementation paths, exact absolute Asknova `.dc.html` reference paths and relevant sections/states, the absolute `src/pages/demo.astro` repository path with the `/demo` anchor, and verification results. Do not start or link a development server.

After review:

- If changes are requested, keep `IN PROGRESS`, update the notes, and revise the same component.
- If approved, set it to `DONE`, record the approval date, remove its standalone `/demo` showcase, and record that removal in the session log.
- The owning session must not move another component to `IN PROGRESS` until its previously approved component has been removed from `/demo`.
- Only after successful user review, create a narrowly scoped commit containing that session's component work and no other session's changes.

## Parallel Session Git Safety

The worktree and Git index are shared by every session. Existing changes must be treated as another session's work unless ownership is explicitly recorded.

1. Before editing and again before committing, inspect both staged and unstaged paths.
2. Maintain an exact list of files and shared-file hunks changed by the current session.
3. Never use broad staging commands such as `git add .`, `git add -A`, or a directory-wide add.
4. Do not unstage, revert, rewrite, delete, or format another session's work to make a commit easier.
5. After user approval, stage or commit only exact session-owned paths. When unrelated staged changes already exist, use a path-limited commit that excludes them.
6. A shared file such as this tracker or `/demo` must not be committed wholesale when it contains another session's changes. Include only an isolated owned hunk when that can be done safely; otherwise leave the shared-file change uncommitted for a coordination commit.
7. Verify the resulting commit's file list immediately after committing. Do not amend or rewrite a commit that may contain another session's work.

## Approved Language Dropdown

`M-30 LanguageDropdown` is an additional Header-owned component approved from the user-supplied dropdown reference on 2026-07-28. This records the intended UI and language list; it does not activate new repository locales by itself.

| Locale | Display label |
| ------ | ------------- |
| `en`   | English       |
| `es`   | Español       |
| `fr`   | Français      |
| `pt`   | Português     |
| `ru`   | русский       |
| `it`   | Italiano      |
| `de`   | Deutsche      |

Required behavior:

- The closed trigger shows the active short locale code, such as `en`, with a chevron.
- The open menu appears below the trigger, highlights the selected language, and gives every option visible hover and focus states.
- The trigger exposes expanded state and menu ownership to assistive technology.
- Keyboard support includes Enter/Space to open, Arrow keys to move, Enter to select, and Escape to close and return focus.
- Clicking outside closes the menu.
- On mobile, the menu stays inside the viewport, uses accessible touch targets, and becomes vertically scrollable if available height is limited.
- Language options and the selected locale are passed into the component. The component must not hardcode active-locale policy or activate translations.
